## บทสรุปปัญหาและจุดเสี่ยง
- ชนิดข้อมูลใน `@shopflow/types` ไม่ครอบคลุมตาราง/ฟิลด์ที่ `@shopflow/api` อ้างอิง (เช่น `payments`, `inventory_movements`, `branch_settings`) ทำให้ build ล้มเหลว
- โค้ดใน `@shopflow/api` อ้างฟิลด์ไม่ตรงกับชนิดปัจจุบัน (เช่น `orders.total_amount` แต่ชนิดกำหนด `total`, `products.stock_quantity` แต่ชนิดใช้ `stock`)
- CMS ใช้ React Query v5 แต่มี options เก่าจาก v3 (`cacheTime`) และค่าผลลัพธ์ `unknown`/implicit `any` จำนวนมากในหน้ารายงาน/คำสั่งซื้อ
- ส่วนหนึ่งของ CMS ยังเรียก Supabase ตรง แทนผ่าน `@shopflow/api` ทำให้โค้ดซ้ำและยากต่อควบคุม
- การจัดการ env/secrets ในบางแพ็กเกจมี fallback ที่ไม่ปลอดภัย ต้องยึดค่าผ่าน env เท่านั้น

## เป้าหมาย
- ทำให้ `@shopflow/api` build ผ่าน พร้อมชนิดตรงกับสคีมาจริง
- ทำให้ CMS type-check ผ่าน โดยปรับให้สอดคล้อง React Query v5 และใช้ shared packages
- ลดโค้ดซ้ำ/แตกต่างระหว่างแอป โดยรวมผ่าน `@shopflow/api`, `@shopflow/types`, `@shopflow/hooks`, `@shopflow/ui`
- เสริมความปลอดภัย, เพิ่มการทดสอบ, เตรียม CI/CD

## แผนการดำเนินงานตามเฟส
### เฟส 1: จัดระเบียบ Shared Types และ API ให้ build ได้
- ปรับ `packages/types/src/Database.ts` ให้ครอบคลุมตารางต่อไปนี้ (ตามสคีมาที่ใช้งานจริง):
  - `payments` หรือ `payment_transactions` (ตามบริการใน `packages/api/src/services/paymentTransactionService.ts`)
  - `inventory_movements`
  - `branch_settings`
- ทบทวน/ปรับชื่อฟิลด์ให้สอดคล้องกับบริการ:
  - `orders`: ใช้ `total` แทน `total_amount` ในบริการ หรือเพิ่มฟิลด์ในชนิดและสคีมาให้ตรง หากธุรกิจต้องการทั้งสอง
  - `products`: ใช้ `stock` แทน `stock_quantity` และ mapping ฟิลด์สำหรับราคา/ส่วนลดให้ตรง
- แก้ `@shopflow/api`:
  - แก้ path export types ใน `packages/api/src/index.ts` ให้ชี้ไปที่ไฟล์จริง (เช่น `./types/api`)
  - ปรับบริการ `coreService`, `orderService`, `reportService`, `systemService` ให้เรียกฟิลด์ตรงกับชนิดใหม่
  - ทบทวน peerDependencies และนำ `react-query` ออก (API ไม่ควรพึ่ง frontend lib)
- ผลลัพธ์: รัน `npm run build` ใน `packages/api` ผ่านได้พร้อม type safety

### เฟส 2: ปรับปรุง CMS ให้สอดคล้อง React Query v5
- อัปเดตทุก hook ใน `apps/cms-web/lib/hooks/*`:
  - ลบ `cacheTime` และแทนด้วย `gcTime`/`staleTime` ตามเหตุผลการใช้งาน
  - กำหนดชนิดชัดเจนให้ `useQuery` ด้วย generic types และปรับค่าผลลัพธ์จาก `unknown` เป็นชนิด domain ที่ถูกต้อง
  - กำจัด implicit `any` ในทุก `.map/.reduce/.filter` ด้วยชนิดจาก `@shopflow/types`
- ปรับหน้ารายงาน/คำสั่งซื้อให้ใช้ผลจาก hooks ใหม่ และลดการคำนวณซ้ำใน render
- ผลลัพธ์: `npm run type-check` บน CMS ผ่าน โดยไม่มี error v5/implicit any/unknown

### เฟส 3: รวมการเข้าถึงข้อมูลผ่าน `@shopflow/api`
- ย้าย service ฝั่ง CMS (เช่น `lib/services/*`) ไปใช้ `@shopflow/api` แทนการเรียก Supabase โดยตรง
- ปรับ hook ของ CMS ให้ใช้ `@shopflow/hooks` เมื่อมีฟังก์ชันเทียบเท่า เพื่อรวมโลจิก cache/pagination/error-handling
- ลบประกาศโมดูลชั่วคราว `apps/cms-web/types/shopflow-api.d.ts` เมื่อ `@shopflow/api` สร้าง type export สมบูรณ์

### เฟส 4: ความปลอดภัยและ env
- ยืนยันว่าไม่มี fallback key/URL ในทุกแพ็กเกจ (เฉพาะค่า env เท่านั้น)
- จัดทำ `.env.local.example` ให้ครบและจัดเอกสารตัวแปรที่ต้องตั้ง
- ตรวจทาน Guards/Permission ใน CMS ให้สอดคล้องบทบาทจริง และไม่รั่วข้อมูล

### เฟส 5: การทดสอบ
- Unit tests: `@shopflow/api` services, `@shopflow/utils`
- Integration tests: query สำคัญกับ Supabase (ใช้ DB ทดสอบ/seed)
- E2E: flow สร้างออเดอร์ → ชำระเงิน → รายงานใน CMS/การขาย POS
- เก็บตัวอย่างข้อมูลทดสอบให้ครอบคลุมกรณีธุรกิจ

### เฟส 6: CI/CD และคุณภาพ
- ตั้ง pipeline: lint, type-check, build, unit/integration/e2e
- ตรวจวัด bundle size, performance (หน้า heavy list/report) และตั้งเกณฑ์
- Docker/Nginx: ทวน config และจัดการ secrets ใน pipeline

## เกณฑ์สำเร็จและการตรวจสอบ
- `@shopflow/api` build ผ่าน และบริการทั้งหมดสอดคล้องกับชนิดและสคีมาจริง
- CMS `npm run type-check` ผ่าน และไม่มี error จาก React Query v5/implicit any/unknown
- หน้าหลัก (Products, Categories, Orders, Reports) ใช้ shared packages อย่างสม่ำเสมอ
- มีชุดทดสอบครอบคลุมฟังก์ชันหลัก และ pipeline ทำงานครบ

## แผนการส่งมอบ
